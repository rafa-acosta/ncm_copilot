VibeCoding — Compliance Remediation Advisor (LLM-powered) — Claude Code Build Prompt
Context
This is the third component of the VibeCoding project, alongside the existing:
·	controls.yaml — single source of truth for the 18 security controls (control_00001–control_00018)
·	Compliance Checker — validates a device's running-config against controls.yaml and produces a compliance report
·	Golden Config Creator — renders a full IOS-XE config from device_vars.json + controls.yaml via Jinja2
This new component, the Compliance Remediation Advisor (CRA), consumes the Compliance Checker's output report and produces a human-readable remediation briefing: what's missing, why it matters, and the exact next steps (commands) to fix it — generated by a small specialized LLM (Phi-3, or similar), not just templated text.
controls.yaml remains the single source of truth. The LLM does not invent remediation steps from scratch — it receives the relevant control's remediation_recommendation, configuration_example, risk, and severity fields as grounding context, and its job is to synthesize and explain, in the tone of a senior Cisco network security engineer, not to hallucinate new commands.

Goal
Build a CLI tool, vibecoding-advise, that:
1.	Reads a Compliance Checker report (JSON) identifying which controls PASSED / FAILED / NOT-APPLICABLE for a given device.
2.	For each FAILED control, pulls the corresponding control block from controls.yaml (risk, severity, remediation_recommendation, configuration_example, variables).
3.	Sends this grounded context to a local LLM (Phi-3-mini or similar small specialized model) with a system prompt establishing it as a Cisco IOS-XE security hardening expert.
4.	Produces a structured remediation briefing, ordered by severity (High → Medium → Low), with:
o	Plain-language explanation of what's missing and why it's a risk
o	The exact next-step command block to apply (pulled from controls.yaml, not invented)
o	Any variables the operator still needs to fill in (e.g., <tacacs_group_name>)
5.	Outputs both a Markdown report (for humans) and a JSON structure (for chaining into other tools, e.g., feeding straight into the Golden Config Creator's device_vars.json).

LLM Backend Architecture (critical requirement)
The tool must support pluggable local LLM backends, selected at runtime or via config, not hardcoded to one engine. Rationale: vLLM and llama.cpp solve different problems (see decision table below), and this tool should be able to use whichever is already running.
Supported backends
Backend	When it's selected	Connection
vLLM	Default when serving multiple devices/reports concurrently, or when a shared team server is already running vLLM	OpenAI-compatible endpoint, typically http://<host>:8000/v1
llama.cpp server (llama-server)	Default for single-device, single-operator, laptop/lab use — lower overhead, no Docker/GPU required	OpenAI-compatible endpoint, typically http://127.0.0.1:8080/v1
Manual override	--backend vllm / --backend llamacpp / --backend auto flag	N/A

Backend selection logic
·	--backend auto (default): the tool pings both endpoints (configurable URLs via config.yaml or env vars VIBECODING_VLLM_URL / VIBECODING_LLAMACPP_URL) and picks the first one that responds to /v1/models. Log which one was selected.
·	If both are reachable, prefer vLLM when the report contains more than one device (batch mode — vLLM's continuous batching wins here); prefer llama.cpp for a single-device report (lower latency for one-shot queries, no batching overhead).
·	If neither is reachable, fail with a clear error telling the operator to start one of the two servers, and print the exact launch command for both as a hint:
·	# vLLM
vllm serve microsoft/Phi-3-mini-4k-instruct --port 8000

# llama.cpp
llama-server -m phi-3-mini-4k-instruct-q4.gguf --port 8080

·	All backends are called through a single internal LLMClient abstraction using the OpenAI Python SDK pointed at the local base_url — no backend-specific code paths beyond the health check and base_url selection. This keeps the tool engine-agnostic if a third backend (TGI, LM Studio) is added later.
Model expectations
·	Target model: Phi-3-mini (3.8B) or similarly small instruct model, quantized (GGUF Q4/Q5 for llama.cpp, AWQ/GPTQ for vLLM) — small enough to run on a lab workstation, good enough for structured technical synthesis from grounded context (this is NOT a free-form generation task; the model is explaining and reformatting known-good data, which small models handle well).
·	The tool must NOT depend on internet access or any external API — fully local, matching the air-gapped/lab nature of the ACME environment.

System Prompt for the LLM (embed this in the tool)
You are a senior Cisco IOS-XE network security engineer performing a post-audit
remediation briefing. You will be given:
1. A control definition (risk, severity, remediation recommendation, and a
   known-good configuration example) from the organization's approved
   compliance framework.
2. The specific non-compliance finding detected on a device.

Your job:
- Explain in 2-3 plain-language sentences what is missing and why it matters,
  as if briefing a network engineer who has 5 minutes before a maintenance window.
- Restate the exact remediation commands EXACTLY as provided in the
  configuration example — do not invent, modify, or "improve" the commands.
- List any <PLACEHOLDER> variables the operator must still supply.
- Do not speculate about the device's environment beyond what is given.
- Keep the tone direct and operational, not academic.


CLI Interface
vibecoding-advise --report path/to/compliance_report.json \
                   --controls controls.yaml \
                   --backend auto \
                   --output-md briefing.md \
                   --output-json briefing.json \
                   [--severity-min medium] \
                   [--device-vars device_vars.json]   # optional, to cross-reference which variables are already known

·	--severity-min: filter to only include findings at or above this severity (default: include all).
·	--device-vars: if provided, the tool checks which <PLACEHOLDER> variables are already resolved in the device's vars file and flags only the ones still genuinely missing — avoids telling the operator to fill in a variable they already set.

Tech Stack (additions to existing project)
·	openai (Python SDK, used purely as an OpenAI-compatible client against local endpoints — no external calls)
·	Existing: ciscoconfparse2, Jinja2, click, pytest
·	httpx or requests for the backend health-check ping

Acceptance Criteria
1.	Tool runs fully offline against a local vLLM or llama.cpp endpoint — no external API keys required.
2.	--backend auto correctly detects and prefers the right engine per the rules above; explicit --backend flag always overrides auto-detection.
3.	Every remediation command shown to the operator is byte-for-byte sourced from controls.yaml's configuration_example/remediation_recommendation fields — never LLM-generated command text. Add a test asserting this (compare LLM output substrings against the source control block).
4.	Findings are grouped and sorted by severity (High → Medium → Low).
5.	JSON output schema is stable and documented, so the Golden Config Creator can eventually consume it directly to pre-fill device_vars.json.
6.	pytest suite covers: report parsing, backend selection logic (mock both endpoints up/down), and the "no invented commands" guarantee.
7.	Clear, actionable error message when no local LLM backend is reachable (including the launch-command hints shown above).

## Implementation Notes (this build)

- The Compliance Checker (`main.py`) didn't emit JSON at all before this component existed — `report_schema.py` (pydantic `ComplianceReport`/`ControlReportEntry`) and `report_generator.render_json`/`build_report_json` were added, plus a `--formats json` option on `main.py`, to give the CRA something to actually consume.
- Field names: this prompt's illustrative `remediation_recommendation`/`configuration_example` don't match `controls.yaml`'s real fields (`remediation`/`config_example` — see `CLAUDE.md`). The real field names are used throughout; `controls.yaml` stays the single source of truth.
- **Command-sourcing guarantee, strengthened beyond this prompt's literal design**: rather than having the LLM "restate the exact commands" (a probabilistic guarantee, verified after the fact), the LLM is never shown the command block at all — it only receives risk/severity/finding context and writes the explanation prose. `remediation_advisor.py` inserts `controls.yaml`'s `config_example` verbatim itself. This makes acceptance criterion 3 true by construction rather than by trusting the model complied — decided with the user before implementation.
- The entrypoint is `vibecoding_advise.py` (run as `python vibecoding_advise.py ...`), not a packaged `vibecoding-advise` console script — this repo has no packaging/console-script infrastructure (same reasoning as `golden_config_main.py` for the Golden Config Creator).
- `briefing.json` includes a `suggested_device_vars_patch: {control_id: {var: null, ...}}` block shaped exactly like `device_vars.json`, concretely realizing acceptance criterion 5.
- Backend selection was originally a hardcoded vLLM-vs-llama.cpp binary choice matching this prompt literally. It was later generalized into a named-backend registry (`--backend auto|<name>`, loaded from `local-llm/config.yaml`) once real hardware constraints (6GB VRAM, two different *models* rather than two different *engines* needed) made the binary choice the wrong shape — see `LOCAL_LLM_SETUP_PROMPT.md`.
- See `LOCAL_LLM_SETUP_PROMPT.md` for how the actual local backend(s) this tool talks to are provisioned and run.
